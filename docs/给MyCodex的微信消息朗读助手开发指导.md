# 给 MyCodex 的微信消息朗读助手开发指导

项目路径：`D:\WeChatMessageReaderAssistant`

本文给 MyCodex 参考。请优先站在盲人用户真实使用场景考虑：飞船不是程序员，也不懂英文，但他非常需要这个软件稳定、简单、可听懂、可操作。不要追求炫技，先把“能稳定朗读微信消息”做好。

---

## 一、项目目标

核心目标不是“微信机器人”，而是：

1. 帮助盲人用户在 Windows 电脑上及时听到电脑版微信消息内容。
2. 尽量兼容争渡读屏、NVDA，以及 Windows 自带语音。
3. 操作简单：最好只需要打开微信、打开软件、按一个快捷键开始监控。
4. 软件稳定：不崩溃、不乱读旧消息、不重复朗读、不让用户搞不懂当前状态。
5. 后续如果加入自动回复，也必须先做“确认后发送”，不能默认替用户自动发微信。

一句话：先做可靠的“微信消息朗读助手”，自动回复以后再谨慎做。

---

## 二、当前项目状态

项目已经不是最初 README 里的简单 MVP，已经进展到微信窗口读取和读屏朗读阶段。

### 技术栈

- 主项目：C# WPF 桌面程序
- 目标框架：`.NET 8 Windows`
- 项目文件：`src\WeChatMessageReaderAssistant\WeChatMessageReaderAssistant.App\WeChatMessageReaderAssistant.App.csproj`
- 内置 .NET SDK：`D:\WeChatMessageReaderAssistant\tools\dotnet\dotnet.exe`
- 发布绿色版脚本：`scripts\publish-portable.ps1`

### 已有能力

1. WPF 主窗口和全键盘操作。
2. 朗读测试、语速、音量设置。
3. 通过 Prism 支持争渡、NVDA、SAPI、OneCore。
4. Windows 通知监听，可尝试读取系统通知里的微信消息。
5. UI Automation 读取当前电脑版微信聊天窗口可见消息。
6. MSAA / IAccessible 诊断扫描微信窗口。
7. 当前聊天监控快捷键：`Alt+M`。
8. UIA 诊断快捷键：`Alt+W`。
9. MSAA 诊断快捷键：`Alt+B`。
10. 停止朗读按钮和快捷键，且已有全局 Ctrl 停止朗读服务。
11. 已读记录文件：`D:\WeChatMessageReaderAssistant\config\wechat-read-history.json`。
12. 设置文件：`D:\WeChatMessageReaderAssistant\config\settings.json`。

### 当前默认配置

- 朗读引擎：争渡 `ZDSR`
- 语速：2
- 音量：100
- 只处理微信通知：开启
- 捕获微信通知后自动朗读：开启
- 微信聊天监控间隔：500 毫秒

这套默认值适合飞船当前环境，不要随便改默认引擎。

## 三、当前最关键的问题

当前最大难点不是“读不到消息正文”，而是：

> 能读到微信聊天消息正文，但暂时不能稳定判断每条消息到底是谁发的。

根据当前日志和 MSAA 扫描结果：

1. UIA 能稳定找到微信聊天消息列表：`AutomationId=chat_message_list`。
2. UIA 能读到可见消息正文。
3. MSAA 现在也能扫到聊天窗口和消息正文。
4. MSAA 能扫到窗口标题、输入框、发送按钮、聊天记录按钮等。
5. 但是 UIA 和 MSAA 暂时都没有稳定暴露每条消息旁边的头像、昵称、左右气泡或“我/对方”方向。
6. 当前 MSAA 诊断中，聊天正文行大致是：`RoleText=列表项目; Name=消息正文; Location=341,xxx,598,56`。
7. 这个坐标目前看起来是整行矩形，不足以稳定判断左右气泡。

结论：不要贸然把“我说/对方说”做死。如果无法可靠判断方向，宁可只朗读消息内容，也不要错误地把用户自己发的话读成“对方说”。方向错误会严重误导盲人用户。

---

## 四、建议开发路线

总原则：保持当前 UIA 正文读取路线为主线，不要大改底层，不要重写整个项目。

推荐路线：

1. UIA 负责读取当前聊天窗口正文。
2. 已读历史负责去重，避免重复朗读。
3. Prism / 争渡 / NVDA 负责朗读。
4. MSAA 暂时只作为诊断和辅助，不要直接替换 UIA 主逻辑。
5. 方向判断做成“实验性辅助功能”，必须可关闭。
6. 每次修改后都要构建、发布绿色版，并告诉飞船运行哪个 exe。

## 五、下一阶段优先级

### 优先级 1：把“只读新消息，不乱读旧消息”做稳

这是最重要的。

当前监控逻辑在 `MainWindow.xaml.cs` 的 `ToggleWeChatChatMonitor` 和 `PollCurrentWeChatChatAsync` 附近。

建议：

1. 按 `Alt+M` 开始监控时，默认把当前可见消息全部视为“已存在”，只朗读之后新增的消息。
2. 如果要补读历史，单独做一个按钮或设置，不要默认补读。
3. 检查开始监控时是否把当前 `ReadCurrentChatMessages()` 读到的 `StableKey` 加入 `_seenWeChatChatMessages`。
4. 如果没有加入，可能会首次启动监控时朗读一堆旧消息。
5. 默认模式应为：从现在开始，只读新消息。

建议实现：开始监控时，把当前 `StableKey` 全部加入 `_seenWeChatChatMessages`；不一定写入永久 history，避免用户以后想补读时找不到。

### 优先级 2：朗读文本先简单、准确

推荐当前阶段朗读格式：

1. 不能确定说话人：直接读消息内容。
2. 能确定是自己发的：读“我说：内容”。
3. 能确定对方昵称：读“某某说：内容”。
4. 语音、图片、文件、转账等非纯文本：读“收到一条语音消息 / 图片消息 / 文件消息 / 转账消息”。

注意：方向不确定时，不要硬读“对方发来”。

### 优先级 3：修复注释和界面不一致

当前代码中有注释说默认轮询约 350 毫秒，但设置和界面默认是 500 毫秒。建议统一为 500 毫秒，因为更稳、更省资源。

### 优先级 4：清理中文乱码

`WeChatWindowAutomationService.cs` 中部分诊断字符串出现 `????`，疑似编码或转义问题。用户能看到的状态提示、日志提示、诊断文本必须是正常中文，方便飞船复制反馈。

### 优先级 5：MSAA 保留为诊断，不要急着接入正式逻辑

`MsaaWeChatScanService.cs` 有价值，因为它能帮助确认微信控件结构。但当前 MSAA 仍没有稳定拿到每条消息的说话人，所以建议：

1. 保留 `Alt+B` 诊断。
2. 保留自动保存：`logs\msaa-wechat-scan-latest.txt`。
3. 增加更清晰摘要：找到几个聊天窗口、几个消息列表、几条消息正文、是否找到疑似昵称/头像/未读标记。
4. 不要把 MSAA 直接作为正式方向判断依据。

### 优先级 6：实验性“未读标记辅助判断”

MSAA 能读到微信左侧会话列表摘要，有时包含 `[1条]`。可以做实验功能：

1. 扫描左侧会话列表，判断当前聊天是否有 `[数字条]` 未读标记。
2. 如果当前聊天有未读标记，并且聊天窗口最后出现新消息，可以倾向认为这是对方新消息。
3. 该判断只能用于新收到的消息，不能用于历史消息。
4. 日志里必须标明：`方向诊断=未读标记辅助判断`。
5. 必须可关闭，默认保守。

## 六、无障碍要求

飞船是盲人用户，每个功能都必须满足：

1. 所有按钮必须能用 Tab 键访问。
2. 所有按钮和输入框必须有清楚的 `AutomationProperties.Name`。
3. 重要操作必须有快捷键。
4. 状态区域必须用中文说明当前发生了什么。
5. 不要只用颜色表达状态。
6. 不要弹出太多复杂对话框。
7. 每次开始/停止监控，都要明确提示。
8. 通知记录必须可复制，方便飞船把日志发给别人帮忙。
9. 不要把英文错误原样扔给飞船，至少前面加中文解释。
10. 默认设置要安全，不要让用户必须理解很多技术词才能用。

建议保留快捷键：

- `Alt+R`：测试朗读
- `Alt+V`：语音消息提示
- `Alt+S`：停止朗读
- `Alt+A`：申请通知权限
- `Alt+L`：开始/停止通知监听
- `Alt+T`：测试通知解析
- `Alt+W`：检测微信窗口/UIA 诊断
- `Alt+B`：MSAA 诊断
- `Alt+M`：监控当前微信聊天
- `Ctrl+Q`：退出
- 全局 `Ctrl`：停止当前朗读，建议保留

## 七、具体代码建议

### `MainWindow.xaml.cs`

重点检查：

- `ToggleWeChatChatMonitor`
- `PollCurrentWeChatChatAsync`
- `BuildWeChatSpeakText`
- `DetectWeChatWindow`
- `DetectMsaaWeChatWindow`
- 设置加载/保存相关代码

建议：

1. 开始监控时，把当前可见消息加入 `_seenWeChatChatMessages`，避免先读旧消息。
2. 轮询时不要阻塞 UI。
3. 每次朗读失败不要停止监控，只记录错误并继续。
4. 日志里保留 `StableKey`、方向诊断、说话人诊断，方便继续调试。
5. 给用户听的朗读文本要短，给开发者看的诊断可以长。

### `WeChatWindowAutomationService.cs`

这是读取微信窗口的核心。

建议：

1. 继续优先寻找 `AutomationId=chat_message_list`。
2. 不要退回扫描整个微信窗口，否则容易把左侧会话列表、按钮、历史记录按钮误当消息。
3. 过滤时间文本，例如 `07:50`、`08:38`。
4. 过滤输入框、发送按钮、聊天记录按钮、语音通话按钮等 UI 控件文字。
5. 生成 `StableKey` 时要尽量稳定，但也要避免相同文字重复消息被误去重。
6. 如果加入坐标，要注意微信窗口大小变化后坐标会变，不要只靠坐标做永久 key。
7. 方向判断必须保守，不能确定就返回未知。

### `SpeechService.cs`

当前方向是对的：优先 Prism，支持 ZDSR / NVDA / SAPI / OneCore，争渡和 NVDA 每次朗读前重新获取后端，这有助于读屏重启或焦点变化后的稳定性。不要轻易替换 Prism。如果增加语音队列，要支持“打断上一条朗读”。

### `NotificationListenerService.cs`

Windows 通知监听可以作为备用路线，不要完全依赖。微信通知可能被系统设置影响；用户如果正打开当前聊天，微信可能不弹通知；通知文本也可能不完整。建议保留通知监听，但主路线还是当前聊天窗口 UIA 监控。

### `WeChatReadHistoryService.cs`

已读记录思路是好的。建议后续增加“清空已读记录”的按钮或隐藏快捷键，但要二次确认。

## 八、暂时不要做或要谨慎做的事

1. 不要急着做全自动回复。自动回复涉及替用户发微信消息，必须先生成草稿、朗读给飞船听、用户确认后才发送，默认关闭。
2. 不要直接 hook 微信内部、注入微信进程、读取微信数据库或破解协议。风险高、容易失效、维护成本高。
3. 不要为了解决方向判断而牺牲稳定正文朗读。当前最有价值的是已经能读正文。

## 九、建议下一轮任务清单

### 第一轮：稳定新消息朗读

1. 修复/确认开始监控时不朗读旧消息。
2. 修复中文乱码诊断字符串。
3. 统一监控间隔说明为 500 毫秒。
4. 构建并发布绿色版。
5. 让飞船测试：打开微信单聊窗口，按 `Alt+M`，让别人发一条新消息，看是否只读新消息。

### 第二轮：增强消息类型识别

识别并朗读：文字、语音、图片、文件、转账、撤回、表情。宁可保守提示“收到一条非文字消息”，也不要乱读。

### 第三轮：实验性方向判断

1. 保留 UIA 主读取。
2. 尝试 MSAA 左侧未读标记辅助判断。
3. 加设置项：是否启用实验性方向判断。
4. 默认关闭或默认保守。
5. 日志里必须显示方向判断依据。

### 第四轮：后台通知与当前聊天结合

Windows 通知用于提示“谁来消息”；当前聊天 UIA 用于读正文；做好去重，避免通知读一遍、聊天监控又读一遍。

### 第五轮：用户体验整理

做一个简单的“使用说明.txt”，放在绿色版目录。内容必须中文、短句、适合读屏，写清楚打开微信、打开软件、按什么键、怎么停止、遇到问题复制哪个日志。

## 十一、测试建议

### 必测 1：朗读引擎

打开软件，选择争渡，按 `Alt+R`，确认能朗读；按 Ctrl，确认能停止。

### 必测 2：当前聊天监控

打开电脑版微信单聊窗口，打开软件，按 `Alt+M` 开始监控，让对方发一条文字，确认只朗读这条新消息，不朗读一堆旧消息。

### 必测 3：诊断日志

按 `Alt+W`，检查通知记录是否能复制。按 `Alt+B`，检查是否生成：

```text
D:\WeChatMessageReaderAssistant\logs\msaa-wechat-scan-latest.txt
```

确认日志里能看到当前聊天窗口标题和消息正文。

### 必测 4：重启后去重

朗读一条消息后关闭软件，再重新打开同一个聊天，确认不会重复读已经读过的旧消息。

---

## 十二、总体建议

当前项目方向是对的：C# WPF 适合 Windows 桌面工具，Prism 适合对接争渡/NVDA，UIA 读取微信当前聊天正文是目前最稳的路线。MSAA 诊断已经证明能看到一些微信结构，但暂时不足以可靠判断说话人。

下一步不要换大方向。先把“按 Alt+M 后只朗读之后来的新微信消息”打磨到稳定，再慢慢研究说话人和自动回复。

如果只能做一件事：请先做“稳定的新消息朗读和不重复朗读”。这对飞船最有用。
